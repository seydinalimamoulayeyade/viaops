01 · le problème ci/cd
// avant jenkins
Chaque commit nécessitait des étapes manuelles : build local, tests à la main, déploiement SSH. Résultat : oublis fréquents, tests sautés, bugs en production, équipes bottleneck. Jenkins automatise toute la chaîne — chaque commit déclenche build, test et déploiement automatiquement.
Analogie
Jenkins est comme une chaîne de production automobile. Chaque pièce (commit) passe par les mêmes étapes dans le même ordre — inspection (tests), assemblage (build), validation (deploy staging). Zéro improvisation, zéro oubli.
02 · concepts clés
// concepts jenkins
ConceptDescription
PipelineFichier Jenkinsfile versioned avec le code. Définit toutes les étapes (stages) du CI/CD.
StageÉtape logique : Build, Test, Deploy. Chaque stage contient plusieurs steps.
AgentMachine (node) où Jenkins exécute le pipeline. Peut être Docker, VM, ou Kubernetes pod.
Declarative vs ScriptedDeclarative = syntaxe simple, structurée. Scripted = Groovy pur, plus flexible mais complexe.
WebhookGit déclenche automatiquement Jenkins à chaque push via un webhook HTTP.
ArtifactFichier produit par le build (JAR, image Docker) stocké pour déploiement ultérieur.
// types de pipelines
  • ▸Freestyle : interface graphique cliquable, limité, legacy.
  • ▸Declarative Pipeline : Jenkinsfile moderne, syntaxe claire, recommandé.
  • ▸Multibranch : détecte automatiquement les branches avec Jenkinsfile et build chacune.
03 · commandes de référence
// jenkinsfile — declarative pipeline
Jenkinsfile pipeline déclaratif · node.js 
pipeline {
  agent {
    docker { image 'node:20-alpine' }
  }

  environment {
    CI = 'true'
  }

  stages {
    stage('Install') {
      steps {
        sh 'npm ci'
      }
    }

    stage('Test') {
      steps {
        sh 'npm run test'
      }
    }

    stage('Build') {
      steps {
        sh 'npm run build'
        archiveArtifacts artifacts: 'dist/**'
      }
    }

    stage('Deploy') {
      when { branch 'main' }
      steps {
        sh './deploy.sh production'
      }
    }
  }

  post {
    always {
      junit 'test-results/*.xml'
    }
    failure {
      mail to: 'team@company.com',
           subject: "Pipeline Failed: ${env.JOB_NAME}"
    }
  }
}
// commandes jenkins cli
bash jenkins cli

docker run -d -p 8080:8080 -p 50000:50000 \

05 · ce qu'il faut dire en entretien recruteur
// questions fréquentes · réponses attendues
▸ "Pourquoi utiliser un Jenkinsfile plutôt qu'une config graphique ?"
"Le Jenkinsfile est versionné avec le code — chaque branche a son propre pipeline. C'est auditable, reproductible et collaboratif via Git."
▸ "Différence entre agent any et agent docker ?"
"agent any utilise n'importe quel agent disponible. agent docker lance un conteneur éphémère avec l'image spécifiée — isolation garantie, environnement reproductible."
▸ "Comment gérer les secrets dans Jenkins ?"
"Avec Jenkins Credentials. On stocke les secrets (tokens, passwords) dans Jenkins et on y accède via withCredentials() dans le pipeline — jamais en clair dans le code."
